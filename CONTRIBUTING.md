# Contributing to exactdoc

Thank you for helping. exactdoc turns PDFs into Word documents that look like
the original and can still be edited, and every part of it is measured. This
guide covers how to report a problem, set up a development copy, run the
tests, check that your change makes the output better, and send a pull
request.

## Ways to help

### Report a conversion that went wrong

This is the most useful thing you can send.

1. Run `exactdoc --diagnose your.pdf`. It prints what the converter's
   decisions depend on (the program that made the PDF, its page sizes and
   fonts, and the layout exactdoc found) with **none of the document's text**.
   It converts nothing and writes nothing.
2. Read the output through. Producer and font names can identify an
   organisation; remove anything you would rather not share.
3. Open a [bad-conversion report](https://github.com/ebt55/exactdoc/issues/new?template=bad-conversion.yml)
   and paste it in, with a cropped screenshot of the problem if you can.

A report with `--diagnose` output, the command you ran and what you expected
is the one most likely to be fixed, because it can be reproduced without your
document.

If exactdoc would not install, or stopped with an error you did not expect (a
traceback, or "This is a bug"), use the
[install or crash report](https://github.com/ebt55/exactdoc/issues/new?template=install-or-crash.yml)
instead. **Security problems go through [SECURITY.md](SECURITY.md)**, never a
public issue.

### Improve the documentation

Typos, an unclear step in the [README](README.md) or [docs/usage.md](docs/usage.md),
an error message that did not tell you what to do: all welcome, as small pull
requests. A change that touches only documentation does not need the quality
check below.

### Fix a bug or improve the output

Read [How a fix is judged](#how-a-fix-is-judged) first: it is short, and it is
the difference between a pull request that merges and one that cannot. For
anything bigger than a small fix, open an issue first and describe the
mechanism you want to change, so we can agree on the approach before you
spend time on it.

## Privacy: what never goes into an issue or the repository

- **Never attach a confidential or personal PDF**, DOCX or screenshot to an
  issue or a pull request. Everything there is public, for ever, attachments
  included. Use `--diagnose` output and a cropped screenshot instead.
- **Never add a copyrighted or personal PDF to the repository**, not even as
  a test fixture, not even "temporarily". Git keeps it in history after you
  delete it.
- **Test fixtures for a fix are generated**, not collected: a small
  [reportlab](https://www.reportlab.com/) program in `tests/` draws the
  smallest page that shows the problem, at test time, and no PDF bytes are
  committed. [tests/wp49_fixtures.py](tests/wp49_fixtures.py) and
  [tests/test_cover_page_fit.py](tests/test_cover_page_fit.py) are the
  examples to copy.
- **The measurement corpus is frozen.** The 16 gated documents
  (`testkit/fixtures/`) and the 79 expansion documents
  (`testkit/fixtures_expansion/`) are either generated by this repository or
  public-domain or permissively licensed public documents, each pinned by
  SHA-256 in `testkit/corpus_manifest.json` or `testkit/corpus_expansion.json`
  with its licence recorded ([docs/corpus-expansion.md](docs/corpus-expansion.md)).
  Adding to or changing the corpus moves every number measured on it, so it is
  a maintainer decision; propose it in an issue.
- Local test inputs belong in `my_samples/` or `tmp/`, which git ignores.
  Credentials (`credentials.json`, `token.json`, `client_secret*`) are ignored
  too; check `git status` before every commit anyway.

## Setting up

You need git and Python 3.9 or newer (the published numbers are measured on
3.12). [uv](https://docs.astral.sh/uv/) is optional; `uv.lock` pins every
dependency.

**Linux and macOS**

```bash
git clone https://github.com/<you>/exactdoc && cd exactdoc
python3 -m venv .venv && . .venv/bin/activate
pip install -e ".[test]"
#   or, with uv:  uv sync --extra test   (then prefix commands with `uv run`)
exactdoc --version
```

**Windows (PowerShell)**

```powershell
git clone https://github.com/<you>/exactdoc; cd exactdoc
py -3.12 -m venv .venv; .venv\Scripts\Activate.ps1
pip install -e ".[test]"
exactdoc --version
```

Optional, depending on what you work on:

- **LibreOffice** (`soffice` on the PATH) for the default conversion's
  render-back correction loop and for the tests that render. Without it,
  conversion falls back to one pass and those tests skip. On Windows, point
  `TEMP` and `TMP` at a short directory such as `C:\lotmp\work` before
  anything starts LibreOffice: a long profile path makes it crash with a
  desktop popup.
- **Docker** for [the quality check](#the-quality-check-does-my-change-make-the-output-better)
  (Docker Desktop on Windows and macOS). On Windows, run the check from Git
  Bash, which comes with Git for Windows.
- The `mupdf` extra installs PyMuPDF, which is **AGPL-3.0**. The measurement
  harness uses it as a reference; the converter must never import it (a test
  checks). You do not need it to contribute.

## Running the tests

```bash
python -m unittest discover -s tests          # the whole suite
python -m unittest tests.test_cover_page_fit  # one file
```

Tests that need LibreOffice, PyMuPDF or the pinned fonts skip themselves, so
the suite runs anywhere; this is what the `install` workflow runs on Linux,
Windows and macOS, on Python 3.9 to 3.14.

Five suites are scripts rather than `unittest` classes, so discovery cannot
see them. CI runs them separately, and so should you if you touch what they
cover:

```bash
python tests/test_purity.py
python tests/test_corpus_degradation.py
python tests/test_gate_mutations.py
python tests/test_golden_ir_backend.py
python tests/test_bottom_margin_relief.py
```

A change to the parser can move the golden intermediate representation:
`python testkit/golden_ir.py verify` (and `--backend pdfium`) says so. If the
move is intended, say why in the pull request; goldens are re-recorded with
the maintainer.

## The quality check: does my change make the output better?

One command measures your change against the commit it started from, in the
same pinned environment CI uses, and prints a verdict:

```bash
bash scripts/dev/quality_check.sh
```

The first run pulls the canonical measurement image,
`ghcr.io/ebt55/exactdoc-gate`, at the digest `.github/workflows/gate.yml` pins
(several hundred MB, once). It is the image the `gate` workflow runs in, so the
verdict you get locally is the one CI gets. To name it explicitly, pass
`--image` with the image reference exactly as `gate.yml` writes it
(`ghcr.io/ebt55/exactdoc-gate@sha256:...`). If you cannot pull it, `--build`
builds `docker/gate.Dockerfile` yourself and provisions it once (it needs the
network and takes a while); see *Which environment* below for what that
changes.

The check measures **two commits** (BASE: by default the point where your
branch left `main`; HEAD: your last commit) one after the other, **in the
same container**:

1. the corpus identity check (every fixture byte-identical to its pin);
2. the fidelity gate, strict: `testkit/runall.py` converts the 16 gated
   documents in both lanes (`raw`, the open-loop control, and `product`, what
   ships), renders each DOCX in LibreOffice with the pinned fonts and scores
   it against the source PDF;
3. with `--corpus both`, also the product profile on the 79 expansion
   documents (`testkit/quality_sweep.py`).

Then it compares BASE with HEAD and prints:

- **per document**, better / same / worse, using the tolerances in
  `testkit/gate.py` (the same rule as criterion 8 of the
  [beta bar](docs/beta-bar.md), including its dy_p50 exemption);
- **the gated 16 per lane**, PASS or FAIL on each commit, and any gate
  finding HEAD has that BASE does not;
- which documents' DOCX changed at all;
- **one verdict line**, and an exit code:

| Verdict | Exit | Meaning |
|---|---:|---|
| `LIFTS` | 0 | at least one document better beyond tolerance, nothing worse |
| `NEUTRAL` | 3 | nothing better, nothing worse (expected for refactors and documentation) |
| `REGRESSES` | 1 | a document worse beyond tolerance, a new crash, or a gate finding on HEAD |
| `UNMEASURED` | 2 | the two commits could not be compared; the output says why |

Results go to `.scratch/qc/<base>-<head>-<corpus>/`. **`report.json` is the
part to paste into your pull request**; `verdict.txt` is what was printed; one
log per step says what happened; and `base/` and `head/` hold each side's
numbers and its DOCX files, so you can open the exact documents that changed.

Useful options (`--help` lists them all):

```bash
bash scripts/dev/quality_check.sh --corpus both        # + the 79 expansion documents (much longer)
bash scripts/dev/quality_check.sh --base origin/main   # compare against another commit
bash scripts/dev/quality_check.sh --repeat HEAD        # the determinism proof (below)
bash scripts/dev/quality_check.sh --dry-run            # print the plan, run nothing
```

Only **committed** work is measured (each commit is copied in with `git
archive`), so commit before you run it. Use the default `--corpus gated` while
you work, and `--corpus both` before you open a pull request that changes
conversion.

**Determinism.** The same commit in the same image should write a
byte-identical DOCX every time: the converter reads the clock only to report
timings and to enforce timeouts, and a render that times out is reported as an
error, never as a different DOCX. (The `docProps/` part carries timestamps and
is left out of every comparison.) `--repeat REF` checks this on your machine:
it measures one commit twice and reports `DETERMINISTIC` (exit 0) only if every
DOCX's `word/*.xml` and every number are identical, and `NONDETERMINISTIC`
(exit 4) with the documents that differed otherwise. If you ever see that,
please report it: it is a bug. In an ordinary comparison, a document whose
DOCX did not change between BASE and HEAD is never counted as better or worse;
if its numbers moved anyway, the report lists it as noise.

**Which environment.** Both commits are measured in one container, so the
comparison between them is valid in any image. The gate's PASS or FAIL against
its recorded baseline is stricter: that baseline is bound to the canonical
measurement environment (`testkit/canonical_env.json`: the exact LibreOffice
build, fonts and Python). The published image IS that environment: CI's `gate`
workflow runs the strict two-lane gate inside it on every push and pull
request, and the quality check run in it gives the same strict verdict. An
image you build yourself with `--build` resolves today's packages and is
usually not that environment, so the report then says `NOT canonical: the gate
is indicative`, and counts only the gate findings HEAD has and BASE does not;
CI's strict gate on your pull request is the number of record. On Apple
silicon the published image runs under amd64 emulation (slow); a `--build`
image builds for arm64, which works for the comparison and is never canonical.

**What it does not tell you.** It does not open the DOCX in Microsoft Word or
Google Docs, and it does not see the unseen holdout documents a release is
judged on; the maintainer runs those. Timing is printed for information and
never judged: it depends on your machine.

## How a fix is judged

These rules come from the [beta bar](docs/beta-bar.md) (amendment 6) and from
experience: fixes tuned to one document have repeatedly made others worse.

1. **Name the layout mechanism.** Say what the PDF does and what the converter
   did wrong, in terms that apply to any document: "a right-aligned tab stop
   on the same baseline as left text is read as a second column", not "fixes
   the resume". A change that improves only the document it was written for
   does not merge.
2. **Ship a synthetic fixture.** A test that generates the smallest PDF
   showing the mechanism (reportlab, at test time), converts it and asserts on
   the result, **plus a control**: a similar page whose output must not
   change. See [tests/wp49_fixtures.py](tests/wp49_fixtures.py).
3. **No document-specific constants.** No threshold tuned to one file, and no
   special case keyed on a producer string, file name or page count, unless
   the mechanism really is the producer's; then say so.
4. **The gated 16 pass in both lanes.** The quality check runs the gate.
5. **No corpus regressions.** The quality check with `--corpus both` says
   `LIFTS` or `NEUTRAL`. A regression is not offset by improvements elsewhere.
   If you believe a flagged regression is a measurement artefact, say so in
   the pull request with the evidence; do not change the tolerances.
6. **The Google Docs output changes only with live evidence.** The
   `--output-profile gdocs` path is qualified by uploading to Google Docs and
   reading Google's own export, which needs credentials only the maintainer
   has, and LibreOffice is known to mispredict Docs. Changes to it are
   welcome; the maintainer runs the live check before merging.
7. **The measurement is not part of the fix.** Do not edit the recorded
   baseline (`testkit/gate_baseline.json`), the canonical environment record,
   the corpus or its manifests, the thresholds in `testkit/gate.py` or
   `testkit/beta_readiness.py`, the harness's reading (`testkit/harness.py`),
   or the waivers in a pull request that changes the converter. Those are
   owner decisions; the quality check lists any of them your branch touches.
8. **No new runtime dependency** without discussion first. If one is agreed,
   update [docs/license-audit.md](docs/license-audit.md);
   `tests/test_packaging_metadata.py` fails until you do.

Before a release the converter may be frozen for a few days; pull requests
that change conversion then wait until the release is out.

## Branches, commits and pull requests

1. Fork the repository and branch from `main`: `git switch -c fix-tab-columns`.
2. Keep the pull request **small and focused**: one mechanism, its fixture,
   its test. Unrelated clean-ups go in their own pull request.
3. Write commit messages that say what changed and why ("Read right-tab
   fields as tabs, because ..."), with the mechanism and the measurement in
   the body. `git log` shows the house style.
4. Add an entry to [CHANGELOG.md](CHANGELOG.md) under **Unreleased**, in the
   style of the entries there: the effect a user sees first, then the
   mechanism.
5. Run the tests and the quality check, and paste `report.json` (or at least
   its `verdict`, `gate` and `lanes` parts) into the pull request.
6. Open the pull request. The template asks for the mechanism, the fixture and
   the report; fill in every section, or say why one does not apply.
7. **CI must be green**: the `install` workflow (the test suite and a real
   install on Linux, Windows and macOS) and the `gate` workflow (the strict
   two-lane gate, inside the pinned canonical image).

Do not commit generated output (DOCX files, rendered PDFs, `.scratch/`,
`testkit/batch/`, `testkit/sweep/`); `.gitignore` covers the usual places.

## Code style

- Follow the code around you. There is no formatter; keep lines to about 90
  characters and match the existing naming.
- `exactdoc/` runs on **Python 3.9**: no `match`, no `X | Y` unions evaluated
  at runtime, nothing newer than 3.9's standard library. The `install`
  workflow tests 3.9 to 3.14.
- Comments and docstrings explain **why**: the mechanism, the measurement that
  motivated it, what would break without it. Many modules open with such a
  docstring; read it before you change the module.
- The converter never imports PyMuPDF (`fitz`) unless the user asked for it;
  `tests/test_no_pymupdf.py` converts with it blocked.
- Tests are `unittest`, in `tests/test_*.py`, and must pass or skip cleanly on
  a machine without LibreOffice or Docker.
- Shell scripts are bash with LF line endings (`.gitattributes` enforces
  them), and must work in Git Bash on Windows.

## What to expect from review

exactdoc is maintained by one person. Every issue and pull request is read,
but replies are best effort and can take a week or more; please do not read
silence as a no. To make review quick:

- small pull requests are reviewed first;
- a pull request with the mechanism, the fixture and a quality-check report is
  usually reviewed in one pass;
- the maintainer runs the quality check with `--corpus both` in the canonical
  image if your report does not have it, and the Word and Google Docs checks
  where they apply, and may push small fixes
  to your branch or ask for changes;
- a pull request that needs a decision about the measurement (a baseline, a
  threshold, the corpus) waits for that decision, which is then recorded in
  [docs/beta-bar.md](docs/beta-bar.md) or the CHANGELOG.

If a pull request has had no reply for two weeks, a polite comment is welcome.
